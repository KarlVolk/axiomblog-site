Plans Should Be Programs

August 3, 2026

Planning is the part of my private research agent harness that I have been thinking about recently. Once a user query is complicated enough to be worth planning at all, the plan has to say which subtasks depend on which and which can run independently and concurrently. This post describes where I ended up.

Twenty-five easy questions#

Take a question like: which infectious diseases must a doctor in Germany report to the health authority by name, as opposed to those that only laboratories must report? For each disease, give the ICD-11 code and WHO’s ICD-11 definition, and say whether the statutory term maps to a single ICD-11 entity or to several.

No part of that question alone is hard. The list of diseases sits in one section of one concrete German law. Looking up the ICD-11 code for a named disease is one query against WHO’s classification. Deciding whether a statutory term covers one ICD-11 entity or several is a small judgement, made once per disease. These are 25 easy questions in a trenchcoat.

Note also that the answer is not in any one document. The statute names the diseases in German legal wording and says nothing about ICD-11. ICD-11 defines entities and knows nothing about German reporting duties. Neither source can simply be quoted. The two have to be matched up, disease by disease, and that matching is work, not a passage that can be found.

The same shape appears in other domains: of the current Dow Jones 30 constituents, how many name AI as a risk in their latest 10-K? Finding one company’s filing is easy, reading its risk-factor section for a mention of AI is easy, adding up 30 booleans is easy (the answer seems to be 29. Only for Caterpillar could I not find a risk-flavoured mention of AI).

Agents are unreliable and inefficient at exactly this, because tracking a loop in prose is error-prone. This post is about having the model write that loop instead of performing it:

dow = await ask_agent(
    "Which companies are the current Dow Jones 30 constituents?",
    schema={"tickers": "list[str]"},
)

risks = await map_agents(
    [f"Does {t}'s latest 10-K name AI as a risk factor?" for t in dow["tickers"]],
    schema={"names_ai_risk": "bool"},
)

sum(r["names_ai_risk"] for r in risks)

Find the constituents, ask one question per constituent, count.

Assumptions#

Take the following two basic assumptions:

  1. The strengths of a language model lie in probabilistic reasoning and language understanding.
  2. Work that a deterministic procedure can do should be done by that procedure as long as the language model can interface with that procedure.

They show why nobody lets a language model do non-trivial arithmetic. Instead, the model emits a tool call to evaluate expressions like (1.07**10-1)/0.07. We do this because the model cannot multiply accurately and reliably. Maybe it is possible to do the same for the structured behaviour of the agent.

A loop is a deterministic procedure#

“For each disease on the list, look up the ICD-11 entry and record how the statutory term maps onto it” is a procedure. It has a fixed iteration count and a body that varies predictably. When a simple agent carries it out inside its own context window (a few turns per disease, 25 times), it is doing by sampling something a for loop does deterministically. That is arithmetic in the context window again, one level up.

Letting a language model do this manually comes with a few challenges:

  • Coverage. Nothing ensures that item 17 of 25 is ever visited. The list of what remains lives in the model’s attention over its own transcript, and the answer it eventually gives is a claim about that transcript instead of an actual count.

  • Context drift. Iteration 25 is not executed by the same program that executed iteration 1, because the context it runs in has grown by 24 intermediate results. Every answer so far is still sitting there, and it is competing for attention with the item currently being looked up (cf. context rot and this paper).

  • Parallelism. The 25 independent lookups should take about as long as one. They do not, because the concurrency is not expressible. A token stream is a sequential machine. The work is parallel and the medium has no way to say so.

The standard response to all of this is the orchestrator pattern: a top-level model that dispatches a subagent per task. It fixes the second problem and, in principle, the third, because each subagent gets a fresh context, and the orchestrator can dispatch several at once. But the loop itself is still being run by hand. The orchestrator has to decide, in prose, that there are 25 items and that it has issued 25 calls, and every result comes back into its context. It moves the work off the model without taking the counting off the model.

So the solution I tried is to let the language model write its plan in code chunks. Writing the plan as code fixes all three problems:

  • Coverage by construction. A list has one slot per item. An item that failed to produce an answer is a hole in that list, found by a comprehension, counted by len, refilled by an assignment. In a context-window loop it would be an absence which the model can easily miss.

  • Context economy. Each subagent gets a small, fresh context containing one item, so iteration 25 runs the same way iteration 1 did. The results accumulate in a variable instead of in anyone’s attention.

  • Parallelism by notation. Independent requests written as one expression are a fan-out by construction. Nothing had to decide to parallelise, and independent work that is not parallelised looks visibly awkward on the page (and is detectable by looking at the AST).

Moreover, results can be filtered, checked and aggregated before a final answer is constructed.

Why the plan should be Python#

Python reads like pseudo-code, so there is no need to invent a domain-specific language for dependencies, fan-out and aggregation. They are already present in the form of assignments, comprehensions and function calls. A plan written in Python is information-dense without being verbose, while staying readable. Python is also one of the most heavily represented languages in language model training data, so most models — even fairly small ones — write simple code snippets fluently. If the plan is a program, the model’s fluency in code becomes fluency in decomposition.

My initial design intention was to let the model write a plan that effectively encodes interdependencies between subtasks instead of a simple sequential plan that is often presented as a todo list. It started as Mermaid diagrams for planning, then became structured JSON describing a dependency graph (a DAG), and ended as plain code, because a program already is the dependency graph. Dependencies are data flow between variables, readiness is evaluation order and parallelism is a gather or map.

Emitting code instead of a tool call in a predefined format is not a new idea. Generated programs had already been used for reasoning and for robot control when CodeAct made the general case: use Python as the agent’s single action space, with an interpreter in the loop, and the agent composes tools and revises its actions in light of the previous observation. What the code reaches for there is a library or a tool. Here, it reaches for another agent.

The procedure sequencer#

The top-level agent, which I have been calling a procedure sequencer, emits only the next cell of Python, executed in a session with persistent bindings. It sees the output, then writes the next cell.

It has no research tools. It cannot fetch a filing, search anything, or open a document. It can only call research agents and compute over what they return. Capability shapes behaviour: under that split, delegation is no longer a decision the model has to make.

Following CodeAct, I do not let the model write a whole program that answers the request when executed. Giving the model an interactive environment allows it to emit small code chunks that depend on prior information. A plan written in one go has to guess how many items the first lookup will return and what shape they will be in; a plan written one cell at a time reads the answer and then decides.

Choosing what to do next is judgement under uncertainty, and it stays with the model. Doing it 25 times is not, and it goes to the interpreter.

An agent does not return a value#

Asking a standard subagent something returns a paragraph, and there is no useful way to write for x in paragraph. Counting the hits, filtering to the ones that qualify, joining tickers to filings, retrying the ones that failed: every one of those needs a value, not prose.

The nearest existing relative here is the recursive language model (RLM). There, a long prompt is loaded into a variable inside a Python read-eval-print loop (REPL), and a root model writes code to peek at it, partition it, grep through it, and recursively call language models over the slices. Same medium, adjacent motivation, since the problem RLM addresses is very long prompts.

Two things differ in the approach described here. First, the callee is not a copy of the model reading a slice of an existing input. Rather, it is a research agent that goes and acquires information present in no input at all (similar to what simple orchestrator patterns implement). Second, the return values of the subagents are typed. This enables the model to compute with the research agents’ answers.

Typed calls#

So I modified my agents to take an additional strictly enforced schema argument defining the shape of their answer. The (abridged) cells below are from the run that produced the disease table. The first one asks for the list:

[1] >>> reportable = await ask_agent(
        "What is the complete list of infectious diseases that a doctor in Germany "
        "must report by name to the health authority? ...",
        schema={"disease_names": "list[str]", "legal_reference": "str"},
    )
    {'disease_names': ['Botulismus', 'Cholera', 'Diphtherie', ...],
     'legal_reference': 'Infektionsschutzgesetz (IfSG), § 8 Abs. 1 Nr. 1 '
                        'i.V.m. § 6 Abs. 1'}

The caller declares the shape it needs and the answer arrives validated, as an ordinary Python value in a variable. reportable["disease_names"] is a list of 25 strings, and len() of it is 25. The fan-out primitive, map_agents, requires a schema for the same reason: typed answers make it possible to aggregate results effectively.

Fanning out over the list#

The list is now bound in the session, and the sequencer’s bindings are its entire memory. The next cell turns those 25 names into 25 requests and issues them at once:

[2] >>> names = reportable["disease_names"]
    >>> requests = [
        f"What is the exact ICD-11 code and the official WHO ICD-11 definition for "
        f"the infectious disease '{n}'? State whether this statutory term maps to a "
        f"single ICD-11 entity or corresponds to several."
        for n in names
    ]
    >>> icd = await map_agents(requests, schema={"icd11_code": "str",
                                                "icd11_definition": "str",
                                                "maps_to": "str"})
    [map_agents] 24/25 ok
      [failed 15] 'Tollwut': nothing found to support an answer

Discover, fan out, compute. All 25 research agents ran concurrently, each in its own context, each answering one question about one disease.

Recovering a failed lookup#

One of the 25 came back without an answer. That can happen at any fan-out width, and the sequencer decides what to do about it by writing a few lines of code:

[3] >>> [(i, n) for i, n in enumerate(names) if icd[i] is None]
    [(15, 'Tollwut')]

[4] >>> retry = await map_agents([requests[15]], schema={...})
    [map_agents] 1/1 ok

[5] >>> icd[15] = retry[0]
    >>> results = [{"german_name": n, **info} for n, info in zip(names, icd)]
    >>> len(results)
    25

The comprehension in cell 3 does two jobs at once. It establishes that something is missing, and it names what is missing, because the None sits at the index of the request that produced it. Cell 4 re-runs that request without reconstructing it, since requests[15] is still bound and is the exact string that was sent the first time. Cell 5 puts the answer back in the hole and joins the two lists.

Writing the answer with a loop#

results now holds 25 records, each one field-for-field what a research agent returned. It is now fairly easy to construct an answer (or a draft thereof) programmatically:

[6] >>> answer = f"Doctors report by name under {reportable['legal_reference']}.\n\n"
    >>> for r in results:
    ...     answer += (f"### {r['german_name']}\n"
    ...                f"- **ICD-11 code:** {r['icd11_code']}\n"
    ...                f"- **WHO definition:** {r['icd11_definition']}\n"
    ...                f"- **Mapping:** {r['maps_to']}\n\n")
    >>> len(answer)
    20138

Every ICD-11 definition in that document is the string the research agent returned, put in place by an f-string rather than restated by the model. The document has 25 sections because results has 25 entries, and it is in the order of the statute because that is the order the list came back in.

A second benefit: a few lines of formatting produce 20,000 characters of answer. Emitted by hand, those 20,000 characters are 20,000 characters of sampling, every one of them an opportunity to drift from the value it is supposed to be reproducing.

Open challenges#

While the idea is straightforward, decomposing a problem efficiently can be highly non-trivial and ambiguous. Depending on the sources used, a decomposition into a list-fetch task and an iteration over that list can be the wrong move (when the primary source already contains that specific information).

The through-line is that a plan and a program are the same object, and its form is what decides whether coverage is checkable, whether independent work is visibly independent, and whether a result can be counted rather than claimed. The model still does the part that needs judgement: what to ask, how to split it, what to do when something comes back empty. It just stops doing the part that a for loop was always going to do better.
