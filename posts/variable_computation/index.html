Giving the Transformer Variable Compute

May 28, 2026

In this set of experiments I investigate different methods of incorporating variable compute allocation into the transformer architecture. Since test-time compute scaling relates the number of tokens produced to output quality, we already have a solution to variable compute: every token costs the same, but a request generates as many tokens as the task needs. Here I ask a different question: can a single token cost a variable amount?

Starting with a small-scale character-based transformer, I wanted to see whether compute can be dynamically allocated to each token (character) in a way that improves upon the simple fully-connected and mixture-of-experts architectures.

Note that these experiments are not easily generalizable to full large transformers with a token vocabulary of 100k or even bigger.

Motivation#

A standard transformer spends the same amount of compute on each token. That is, easy-to-predict filler words cost as much as tokens that carry a lot of semantic weight. The main takeaway is that a standard transformer has constant FLOPs/token.

NoteThe picture is a little more subtle than “one token, one fixed budget.” Through attention, an interesting token’s meaning does not stay put. Every subsequent token can read from it, so in the deeper layers its meaning can get reused and further processed by the compute nominally spent on the boring tokens that follow it. One thing that keeps this from dissolving into an undifferentiated soup is the residual connection which carries each position’s original embedding forward, so a token stays anchored to itself even as information mixes.

So an interesting question to ask is:

Can we allocate variable compute dynamically to each token, depending on how much it needs?

The following experiments describe different attempts to answer the question. I followed two main techniques to realize the variable compute:

  1. Use a mixture-of-experts style router to route tokens through compute paths of different costs.
  2. Try to learn a more compute optimal tokenization by using learnable byte-level patching in the architecture. This should modify token count rather than character-token compute.

The main result is that sparsemax token routing matched standard mixture-of-experts while using around 25% less compute with the same parameter count.

The Scope#

The goal here is not better quality on its own, but a better compute-quality trade-off. Plotting each network on a FLOPs/token vs. quality plane traces out a Pareto front, which lets us compare the different methods on equal footing.

As mentioned above, the experiments are rather tiny in scale: we use byte-level (character) encodings and train on the Wikitext-2 corpus. The baseline transformer has an embedding dim of $d=256$ and $8$ layers, trained for $4000$ steps.

The main motivation behind the byte-level encodings is that tokenization itself is a compute allocation mechanism which is currently separately trained for frontier LLMs. The gradient signal during training does not optimize the tokenization, so we are almost certainly left with a suboptimal one. Starting at the byte level lets us fold the tokenization into the model and test learnable variants of it.

To compare the different architecture choices, we need to fix some hyperparameters:

  • Training data: WikiText-2.
  • Optimizer: AdamW + cosine schedule.
  • Architecture: RMSNorm, RoPE, SwiGLU feedforward blocks, weight-tied head.
  • Results: Taking the checkpoint that performed best on the validation set.

Disclaimer: I make no claim to be the first to test these methods (I am sure that I am not). This post documents a set of experiments and discusses them. Not more, not less. Otherwise this would be a paper.

Expert Routing for Variable Compute#

The mixture-of-experts (MoE) baseline works as follows: a linear router scores $E = 8$ experts and routes each token through its top two. For a token hidden state $x \in \mathbb{R}^d$,

$$p = \operatorname{softmax}(W_r\, x), \qquad y = \sum_{i \in \operatorname{top-2}(p)} \tilde{p}_i \, E_i(x),$$

where $\tilde{p}$ renormalizes the gates over the two selected experts, and each expert $E_i$ is a SwiGLU feedforward block of hidden width $2d$ (so two active experts cost roughly one dense $4d$ FFN). A Switch-style load-balancing loss keeps expert utilization roughly uniform. This lets each expert specialize while the router activates only the paths a token needs, keeping inference compute low even as the parameter count grows. This is especially useful for storing vast amounts of knowledge within such a network. The baseline achieved 3.108 ppl @ 19.0M FLOPs with 27.4M parameters.

I tested two methods to achieve variable compute with the token-routing mechanism:

  1. Vary the compute of each routed path. The model can learn to select low compute paths for easier tokens and high compute paths for harder tokens. For this set of experiments this is called mixture-of-compute.
  2. Allow the router to select a variable number of routes. Thus harder tokens get more computation by being routed through more experts. Here we call it adaptive MoE.

Mixture-of-Compute#

For mixture-of-compute I decided to have experts with differing widths. The $E$ experts are SwiGLU blocks with hidden-width multipliers $(0, 1, 2, 4)\times d$, where expert $0$ is a zero-width skip (the identity/residual path, costing no FLOPs). Since a SwiGLU block’s FLOPs scale with its hidden width, each multiplier is exactly that expert’s compute tier. The router is the same top-2 softmax as MoE, but because the selected experts now cost different amounts, the realized compute per token depends on which experts win.

To keep the router from always grabbing the widest (most accurate) experts, we add a Lagrangian compute penalty to the loss (alongside a small router-z regularizer):

$$\mathcal{L} = \mathcal{L}_{\text{NLL}} + \lambda\,\frac{\mathbb{E}\!\left[\sum_i p_i\, c_i\right]}{C_{\text{ref}}},$$

where $c_i$ is expert $i$’s FLOPs cost, $C_{\text{ref}}$ a fixed reference, and $\lambda$ dials the average compute per token. In my experiments this did not beat standard MoE at matching compute, resulting in 3.131 ppl @ 18.8M FLOPs. What the architecture does buy us is a knob to tweak the average compute per token continuously, beyond the discrete steps of “number of active experts”. (The best-matching duplicated variant uses multipliers $(0,1,1,2,2,4,4)\times d$, i.e. two experts at each nonzero cost tier rather than one, giving the router more specialized paths at the same FLOPs.)

Adaptive Mixture-of-Experts#

The idea is simple: use the same experts as the MoE baseline ($E = 8$ SwiGLU blocks of hidden width $2d$), but swap the routing rule. Instead of softmax followed by a fixed top-2, the router applies sparsemax, the Euclidean projection of the logits onto the probability simplex:

$$g = \operatorname{sparsemax}(W_r\, x) = \arg\min_{q \,\in\, \Delta^{E-1}} \lVert q - W_r x \rVert^2 .$$

Unlike softmax, sparsemax assigns exactly zero weight to some experts, so the per-token count $k = \#\{\, i : g_i > 0 \,\}$ becomes data-dependent and learned: peaky logits give a small $k$ (one expert dominating; cheap tokens), near-uniform logits give a large $k$ (hard tokens). No threshold and no straight-through estimator are needed; a permissive cap $k \le k_{\max}$ only bounds memory. The average compute is dialed by penalizing the gates’ inverse participation ratio $1/\sum_i g_i^2$ (a smooth surrogate for $k$) with the same coefficient $\lambda$ as in mixture-of-compute.

This gave us a whopping 3.113 ppl @ 14.3M FLOPs, matching the MoE baseline at almost 25% less compute and the same total parameter count.

I started out with a maximum cap of $k=4$, so that the most expensive tokens could choose up to four experts at once. As it turned out, tightening the cap to only $k=2$ led to fewer FLOPs at the same quality. The gain here was therefore not about allowing more compute, but about saving compute on the tokens that did not need it.

A second surprise is that the compute penalty is not purely a cost; it doubles as a routing regularizer. Across the $\lambda$ sweep (at cap $k=4$), the run with no penalty ($\lambda = 0$) is the worst on both axes, at 3.134 ppl and 20.4M FLOPs, and even routes backwards, spending more compute on whitespace than on letters. A moderate $\lambda = 0.02$ simultaneously yields the best perplexity, the least compute, and correctly-directed per-token spending.

Token Patching#

The second lever changes how many tokens exist. Bytes are cheap individually but there are a lot of them; if we merge them into a smaller number of patches before the expensive transformer stack runs, the model does less work per byte. The catch is that the merging has to be learned and content-aware: the whole point of going byte-level was to not hard-code (or optimize separately) the tokenization.

I compared three ways of forming patches, all at $d=256$ and $8$ layers, against the dense byte-level GPT (3.166 ppl @ 19.0M FLOPs) as reference:

  1. BLT (entropy patching, baseline). Following the Byte Latent Transformer, patch boundaries go where the next byte is hardest to predict. The shared byte encoder (2 attention-only layers, $d=128$, 4 heads) feeds a weight-tied linear next-byte head, a lightweight byte-level LM trained jointly via an auxiliary loss (weight 0.1), not a separate pre-trained model as in the original BLT. Its predictive entropy is evaluated at every position, and the top-$K$ highest-entropy positions become patch boundaries. This scales cleanly: shrinking the average patch size $8 \to 4 \to 2$ trades compute for quality monotonically, going 5.59 -> 4.66 -> 3.66 ppl as realized compute grows 3.1M -> 5.3M -> 9.9M FLOPs.

  2. WPT (warp-pool transformer, a negative result). Instead of discrete boundaries, WPT is fully differentiable: the model emits a per-byte stretch weight and patches are formed by Gaussian soft-pooling along the induced “warped” coordinate. It is elegant, and it fails to scale: the extra compute of smaller patches doesn’t pay off, and patch size $2$ (5.90 ppl @ 9.9M FLOPs) is actually worse than patch size $8$ (5.76 ppl @ 3.1M FLOPs). The failure mode is mass concentration: most bytes receive near-zero stretch, so the extra patches end up nearly empty.

  3. HPT (hierarchical patch transformer, a partial recovery). HPT replaces the single pooling step with three successive learned $2\!:\!1$ merges. At patch size $2$ it nearly matches BLT, reaching 3.81 ppl @ 9.6M FLOPs vs 3.66 @ 9.9M, recovering most of what WPT lost.

The takeaway is that where the boundaries go matters more than how you pool between them: content-aware discrete placement (BLT) beats a clever continuous relaxation (WPT), and stacking discrete merges (HPT) recovers most of the gap. Even so, none of these beat the dense byte baseline at this scale: patching here buys us a compute knob, not a quality win.

Conclusions#

Even at this scale, MoE is surprisingly hard to beat. The only architecture that lands below it on the compute-quality frontier is Adaptive MoE, and it wins by removing compute (a tight $k \le 2$ cap plus a mild routing penalty) rather than adding it. Everything else (variable-width experts, the differentiable warp-pool) trades either parameters or quality for its compute knob.

If there is one theme, it is that adaptive compute pays when the model is allowed to commit: hard per-token $k$ via sparsemax wins, and content-aware discrete patch boundaries scale, while the smoother, hedge-everywhere relaxations (WPT; $\lambda = 0$ Adaptive MoE) do worst. Softer is not automatically better.

Caveats. This is a mechanism study, not a scaling claim: a single seed with no error bars (sub-~1% perplexity gaps may be noise), one model size, one dataset, one sequence length, and byte statistics specific to English. The Adaptive MoE win is small, but it is consistent in the same direction across every $\lambda$ I tried. I also did not compare the different training behaviours, which might reveal other differences.
