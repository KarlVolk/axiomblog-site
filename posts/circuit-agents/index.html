Circuits from a Local Agent

September 21, 2026

This is my venture into a hardware description language and how a custom agent harness can be built to let a locally running LLM (Qwen3.8-27B) autonomously design circuits. An example case is shown at the end of this post.

The Task#

When I first learned about Verilog, the concept of a hardware description language intrigued me since it is not just another imperative language in a new coat of paint. I always wanted to learn more about electronic circuits anyway, so I set out to learn some basic Verilog. Before that, I thought that circuits were drawn by hand with the support of CAD-like software. Once you actually think about it, it becomes clear that, given the complexity of modern circuits, the pipeline from idea to an actual physical circuit consists of many steps at different abstraction and modelling layers. To my current understanding these are roughly:

  • You translate the desired behavior into a kind of logical form that describes the actual circuit at a high-level (at the register-transfer level, which combines boolean circuits/formulas and sequential logic, i.e. time).
  • Then, similar to how a compiler translates your high-level code into an efficient implementation at the machine-level, the logical circuit is translated into technology-specific physical primitives like NAND-gates, NOR-gates and D-Flip-Flops. This step is called logic synthesis and its result is a gate-level netlist.
  • Then size and the input and output pin positions are fixed and the large blocks are arranged. The result is called a floorplan. Within it, the individual components are placed to minimize wire length and routing congestion and optimize for other constraints like component-density.
  • Then clock-tree synthesis, which inserts components like buffers, is used to synchronize the clock and its delays across the circuit.
  • Then the routing of the physical wires is calculated, globally first and then in detail, again subject to costs and congestion.
  • Extract the resistance and capacitance the finished wires actually have, check the timing against those numbers, and verify that the layout still matches the netlist
  • Tapeout: hand the finished layout to the semiconductor foundry, which derives the photomasks from it for fabrication.

Verilog sits at the first step in this chain. It is a way to describe your logic at the register-transfer level. It can be simulated to check your logic for clock cycle-accurate correctness. It is at this level where many decisions are already being made: how do you represent your data, is it processed in sequence or in parallel (which has different speed, space and power implications). It is an interesting language, as it bridges the gap between digital programming and physical hardware development.

Given that it is being reported that models are gaining capabilities of writing Verilog directly, this seemed like the perfect avenue to check out how a specialized agent harness for Verilog could look like and how far we can push even small models in engineering tasks. Especially since the Qwen3.8-Max announcement contained a whole section about automating chip design, hinting at the Qwen team using corresponding data in their training pipelines.

Going from an Idea to a Circuit#

Because of its special place between software and hardware, Verilog development can feel quite different to imperative programming, depending on your established practices. Verilog code can not be executed in the classical sense. It describes either directly or through behavioral descriptions how the logical circuit is connected: a graph of components and wires between their connectors.

So how do you know if your Verilog code does what you want it to do? There are multiple ways to check your Verilog implementation:

  1. You specify inputs or a series of inputs together with the desired outputs. This is called a testbench and it is how you check if your implementation behaves the way you wanted in a simulation. Tests and implementation should ideally be developed independently from each other (design engineers vs. verification engineers) to avoid information leakage and biases.
  2. Test behavior against a golden reference model: Implement your desired behavior in a common high-level programming language like C++ or Python. This serves as the source-of-truth for correct behavior. Probing the Verilog simulation and comparing outputs against the reference model can now reveal errors in your hardware description.
  3. Write a mathematical proof that the Verilog code does what you want, or at least prove desired properties which you specify formally.

Of course, these practices can be combined and to my understanding which are used depends on the scale of the circuits. I thought that a good starting point for automation of smaller circuits was to focus on testbenches. This shifts the focus significantly from “how can we implement this in Verilog” to “how do we test this sufficiently and what do we even test”. This change in perspective frames the problem not as a programming challenge but as a task in requirements management. I wanted to write an autonomous agent that takes my description of what I want and produces working Verilog code.

Playing around with the fantastic Qwen3.8-27B, I found out pretty quickly that, at least for very simple circuits, it could write decent Verilog implementations. The crux is that ambiguities in my description could confuse the model and even worse, the testbenches it writes were not out-of-the-box sufficient and sometimes wrong (e.g. shifting bits to the right instead of left, contrary to my request). This is annoying: it produces the correct Verilog code for simple problems when skipping proper tests, but we know that proper tests are needed for more complicated circuits. So how could we trust the Verilog implementation? The solution I tried was to implement a simple requirements engineering pipeline before letting the model write tests and then the implementation.

The design pipeline I wanted my agent to follow consists of these high-level phases that mimic a typical engineering pipeline:

Request -> Requirements -> Specification -> Testbench -> Implementation

Each arrow represents an independent module. I believe that some steps in this decomposition of the design pipeline might become superfluous with scaling model capabilities. However, I also believe that with scaling model capabilities such a design pipeline allows scaling towards more complex problems. That is, the “harness” scales with model capabilities. Each step could probably be enhanced by quite a bit, given input from someone more knowledgeable and with more experience in this domain. In what follows, I describe how each step works in my pipeline. I will explain the nomenclature of the words requirements and specification, as they can be used in other ways to the one I chose in this pipeline.

Decomposing a problem like this into multiple steps has certain risks to watch out for. On the one hand, each step could introduce mistakes and errors by the model, on the other hand, we also have the ability to implement tests, verifications and supervision at each step which has the potential to improve the overall quality.

Phase 1: Request → Requirements#

INPUT: The user's request.
OUTPUT: A list of requirements, each together with a source reference pointing at the part of the request they come from.

Requirements specify what the system should do as contained in the request. It is, in our case, a natural language description of desired behavior. How that is achieved stays open here, and stays open through the next stage too.

We can already catch higher-level potential inconsistencies at this stage before they become more involved and obfuscated down the line. At this point I could draw from my experience on working (during my thesis) on potential automation of the requirements management process: given a reasonably smart model that can process natural language sufficiently well and has a basic grasp of the needed technical competence (the former point which is nowadays nothing special anymore and the latter which improves from model generation to newer model generations), we can automatically detect inconsistencies in our requirements.

The mechanics of this phase let the agents take the request and produce a list of requirements together with references to the initial request. This anchors the requirements in the request and makes coverage partially testable.

Central Quality Checks:

  • Each requirement comes with a quote from the request. This quote is mechanically checked by matching strings.
  • Each requirement is rechecked against its own quote: does it say only what that part of the request says? This is judged by an LLM.

Phase 2: Requirements → Specification#

INPUT: The list of requirements with their attribution.
OUTPUT:
	- The specification (spec.md)
	- The interface (case.toml)

Specifications are a description of what the system achieves, deciding on ambiguities, filling holes and overall achieving a complete picture of the requirements. It is one step closer towards formal when we imagine that a request is at the informal end of the spectrum.

The interface formally declares the name, ports (inputs and outputs), parameters and the goal. The spec is a written markdown file and the interface is formalized in a toml file.

Central Quality Checks:

  • Per requirement, a model judges if the requirement is correctly contained in the specification file. This is done by quoting where in the spec each requirement appears. The model also mentions if the requirement exists, but in a different form, thereby distinguishing between omission and errors.
  • Per quantity, a model judges whether the specification settles that quantity once or twice. The check above walks the requirement list, so it is blind to anything no requirement raises, and a specification is free to invent an answer the request never asked for and then invent it again differently. Reading every pair of sentences does not scale well, but a contradiction is often about something that both statements name. So the unit is the quantity: one call lists the quantities the document fixes, then one call per quantity reads the whole document with that quantity’s lines marked.
  • Per output port, two more readings of the same kind: can driving the inputs alone ever bring this output to a value the specification determines, and does the specification say what it holds before the circuit has done anything and which edge it changes on relative to its cause.

The specification is written in a REPL, as described below. With the quality checks and feedback inserted appropriately.

Using REPLs to Manage Context, Capabilities and Feedback#

A read-eval-print loop (REPL) describes the way we interact with a terminal: Enter a command, the system prints a response, repeat while keeping a history. In my implementation, I added a state: a fixed block right above the input text field that shows information. This information may change using my commands and does not sit in the history. The most important use-case for this state field is the content of a file. You can represent the file editing loop as a REPL, but instead of making small edits and re-reading the file each turn, which pollutes the context with old states, we just update the view of the file and only keep the command history. Framing file writing and editing as a REPL allows the agent to make small changes without having to rewrite the whole file each time some feedback (Error message, warnings, etc.) nudges the model. That would not only be inefficient, but also increase the chance of introducing new errors (when writing long documents, they may contain errors).

Phase 3: Specification → Testbench#

INPUT:
	- Requirements
	- Specification
	- Interface
OUTPUT: A testbench (tb.v)

The testbench tests the desired behavior, as its rather complete description in the specification document expresses. This was, in my experiments, the hardest part. This step alone was the main reason I introduced the two previous stages. A bad testbench can pass wrong designs as seemingly correct or a correct design as false. Assuming that our specification is good, we can use some best practices to improve testbench quality by a lot. To write the testbench, I reused the REPL framework.

Capture Every Specification: Every behaviour the specification states should lead to a test that succeeds on a correct design and fails on a wrong one.

Write Small Behavioral Code instead of only probing certain binary combinations in the hopes that they don’t miss anything.

The testbench is a Verilog file that instructs the simulator to simulate outputs and then check them against expected outputs. This happens through behavioral descriptions and hardcoded examples. Where the design is clocked, the behavioral comparisons run on every clock edge, against stimulus that is random from a fixed seed.

Quality Checks:

  • The bench runs against a model that sets every output to zero. This is a rough heuristic, but such an empty model should not pass a proper testbench. This is checked every turn.
  • The bench must set all parameters, so it doesn’t just pass by assuming default values.
  • Bench edits name which requirements they cover by id. This is an upper bound proxy on test coverage. In other words, if there is a requirement that has no tests yet, we are missing something.

Phase 4: Testbench → Implementation#

INPUT:
	- Specification (spec.md)
	- An empty module derived from the interface containing only the ports
OUTPUT: The final implementation (<name>.v)

Only now can the coding begin. To avoid reward hacking the programming agent does not actually see the testbench. The coding loop itself is pretty basic: the agent interacts, again, with a REPL that allows it to modify a Verilog file. After each edit it receives feedback on how many tests pass and which tests (by name) fail. This feedback loop runs until no test failures remain and the agent decides to call a finish function.

Quality Checks:

  • All tests must pass before the agent can call the work done. Failed tests are reported back so the agent can repair the code (what the simulation produced vs what it expected at which time).
  • The agent can give up. This is necessary for unfulfillable requests.

Where this leaves us#

Running this pipeline, the harness can use a small Qwen model to produce working Verilog implementations, starting from vague requests like “a traffic light circuit” to detailed markdown documents that describe the behaviour of a stopwatch (see below). Of course, there are heavy limitations. First, the pipeline, as of now, has no proofs of correct behavior, runs slowly (due to all the checks) and its scope is limited heavily by model capabilities. Being able to let a locally running model design simple circuits, on the other hand, is kind of magical and empowering and I expect Verilog capabilities to improve in the coming months. One possibility where one could take such a design next is to incorporate further optimization constraints (like power consumption or circuit area estimates) to further improve the designs in a generate-and-test environment like the REPL we have implemented.

Regarding the quality, I am sure that the checks (mechanical and model-dependent) can be improved and extended. They are a work-in-progress and are probably where domain-experts could add a lot of value.

On Recursive Usage for Complex Designs#

One of the ideas I wanted to test was how we could use a system that is good (enough) at designing simple(ish) circuits to decompose complex problems into manageable pieces. Basically allowing the agent to commission a module and use it without knowing its implementation details. If that step was feasible, then we could even design larger more complicated circuits using limited compute and even more complicated design using much more compute. I plan to describe this in my next post.

# Design Challenge: Tenth-Second Stopwatch

Design a synthesizable Verilog module for a stopwatch that counts tenths of a second and whole seconds, started and paused by a single control input, with its elapsed time exposed directly on output ports.

## Module Interface

| Port Name | Direction | Width | Description |
|---|---|---|---|
| `clk` | Input | 1 | System clock |
| `rst` | Input | 1 | Active-high synchronous reset |
| `start_stop` | Input | 1 | Run/pause control |
| `running` | Output | 1 | High while the stopwatch is counting |
| `tenths` | Output | 4 | Elapsed tenths of a second, 0 to 9 |
| `seconds` | Output | 6 | Elapsed seconds, 0 to 59 |

## Parameters

* `CYCLES_PER_TENTH`: Default `10` (rising edges of `clk` in one tenth of a second).

## Functional Requirements

### 1. Power-on and Reset

* At power-on, before any rising edge of `clk` has occurred, `running` is 0, `tenths` is 0 and `seconds` is 0.
* `rst` is synchronous and active high. At a rising edge of `clk` where `rst` is 1, `running` becomes 0, `tenths` becomes 0 and `seconds` becomes 0.
* Reset takes priority over every other rule: at a rising edge where `rst` is 1, no other rule changes any output.

### 2. Run and Pause

* `start_stop` is level sensitive and is acted on at every rising edge of `clk` at which it is high.
* At a rising edge where `rst` is 0 and `start_stop` is 1, `running` takes the opposite of the value it held before that edge.
* At a rising edge where `rst` is 0 and `start_stop` is 0, `running` holds the value it held before that edge.
* Holding `start_stop` high across several rising edges therefore toggles `running` once at each of them.

### 3. Tick Generation

* A tick occurs at the `CYCLES_PER_TENTH`-th rising edge of `clk` counted from the edge at which `running` most recently became 1, and at every `CYCLES_PER_TENTH`-th rising edge after that for as long as `running` stays 1.
* When `running` becomes 0, any tenth in progress is discarded. When `running` next becomes 1, the count to the next tick begins again from the edge at which it became 1.
* At a rising edge where `rst` is 0 and `start_stop` is 1, no tick occurs, whatever the count had reached. This is the only edge at which a toggle and a tick could coincide, and the toggle wins.

### 4. Time Counters

* At a tick edge where `tenths` is less than 9, `tenths` becomes `tenths + 1` and `seconds` holds the value it held before that edge.
* At a tick edge where `tenths` is 9 and `seconds` is less than 59, `tenths` becomes 0 and `seconds` becomes `seconds + 1`.
* At a tick edge where `tenths` is 9 and `seconds` is 59, `tenths` becomes 0 and `seconds` becomes 0.
* At any rising edge that is neither a reset edge nor a tick edge, `tenths` and `seconds` hold the values they held before that edge.

## Design Rules & Constraints

* **No derived clock logic:** every counter and every state change is synchronized strictly to `clk`. Do not use a tick or `start_stop` as a clock input.
* **Exact widths:** `tenths` holds 0 to 9 in 4 bits, `seconds` holds 0 to 59 in 6 bits.

Phase 2, the specification written from the requirements.

# Stopwatch Specification

## Module

Module name: `stopwatch`

## Parameters

| Parameter | Default | Meaning |
|---|---|---|
| `CYCLES_PER_TENTH` | `10` | Number of rising edges of `clk` in one tenth of a second. Must be ≥ 1. |

## Ports

| Port | Direction | Width | Description |
|---|---|---|---|
| `clk` | input | 1 | System clock. All state changes occur on the rising edge of `clk`. |
| `rst` | input | 1 | Active-high synchronous reset. |
| `start_stop` | input | 1 | Level-sensitive run/pause toggle. Acted upon at every rising edge of `clk` at which it is sampled high. |
| `running` | output | 1 | High while the stopwatch is counting. |
| `tenths` | output | 4 | Elapsed tenths of a second. Valid range 0–9. |
| `seconds` | output | 6 | Elapsed seconds. Valid range 0–59. |

## Initial State (Before Any Rising Edge)

Before the first rising edge of `clk` has occurred, the outputs hold:
- `running` = 0
- `tenths` = 4'b0000
- `seconds` = 6'b000000

## Between Edges

Between rising edges of `clk`, all three outputs hold the value they were assigned at the most recent rising edge. No output changes between edges.

## Rising-Edge Behaviour

Every rising edge of `clk` is classified into exactly one of the following cases. The rules are evaluated in priority order: **Reset > Toggle > Tick > Hold**.

### Case 1: Reset

**Condition:** `rst` = 1.

At this rising edge:
- `running` ← 0
- `tenths` ← 4'b0000
- `seconds` ← 6'b000000
- The internal cycle counter is set to 0.

Reset takes priority over every other rule. No toggle and no tick occur at a reset edge, regardless of the values of `start_stop` or the cycle count.

### Case 2: Toggle (start_stop asserted)

**Condition:** `rst` = 0 and `start_stop` = 1.

At this rising edge:
- `running` ← NOT `running` (toggles to the opposite of its pre-edge value).
- The internal cycle counter is set to 0. (If `running` was 0 and becomes 1, the count to the next tick begins from this edge. If `running` was 1 and becomes 0, the in-progress tenth is discarded.)
- `tenths` holds its pre-edge value.
- `seconds` holds its pre-edge value.

**No tick occurs at a toggle edge**, even if the cycle counter had reached `CYCLES_PER_TENTH` at this edge. The toggle takes priority over any coinciding tick.

Because `start_stop` is level-sensitive, holding it high across N consecutive rising edges (with `rst` = 0) causes `running` to toggle once at each of those N edges.

### Case 3: Tick

**Condition:** `rst` = 0, `start_stop` = 0, `running` = 1, and the internal cycle counter reaches `CYCLES_PER_TENTH` at this edge.

The internal cycle counter works as follows:
- It is set to 0 at the rising edge at which `running` transitions from 0 to 1.
- At every subsequent rising edge while `running` = 1, `start_stop` = 0, and `rst` = 0, it increments by 1.
- A tick occurs on the edge where it reaches the value `CYCLES_PER_TENTH`. After the tick, it is reset to 0.
- The first tick therefore occurs exactly `CYCLES_PER_TENTH` rising edges after the edge on which `running` became 1. Subsequent ticks occur every `CYCLES_PER_TENTH` edges thereafter, for as long as `running` remains 1.

At a tick edge, the outputs update as follows (determined by the pre-edge values of `tenths` and `seconds`):

| Pre-edge `tenths` | Pre-edge `seconds` | Post-edge `tenths` | Post-edge `seconds` |
|---|---|---|---|
| 0 – 8 | any (0 – 59) | `tenths` + 1 | `seconds` (unchanged) |
| 9 | 0 – 58 | 0 | `seconds` + 1 |
| 9 | 59 | 0 | 0 |

At a tick edge, `running` holds its pre-edge value (which is 1).

### Case 4: Hold

**Condition:** `rst` = 0, `start_stop` = 0, and (either `running` = 0, or `running` = 1 but the cycle counter has not yet reached `CYCLES_PER_TENTH`).

At this rising edge:
- `running` holds its pre-edge value.
- `tenths` holds its pre-edge value.
- `seconds` holds its pre-edge value.
- If `running` = 1: the internal cycle counter increments by 1.
- If `running` = 0: the internal cycle counter holds at 0.

## Value Ranges and Wrap

- `tenths` is a 4-bit value that only ever holds 0 through 9. It never reaches 10 or above. When it would wrap from 9, it resets to 0 (governed by the tick rules above).
- `seconds` is a 6-bit value that only ever holds 0 through 59. It never reaches 60 or above. When it would wrap from 59 (which can only happen simultaneously with `tenths` at 9), it resets to 0.

## Synchronisation Constraint

Every state change—reset, toggle, tick, counter increment—occurs strictly on the rising edge of `clk`. Neither `start_stop` nor the tick event is used as a clock input. The design is a single-clock, synchronous circuit.

## Reset Priority Summary

At any rising edge where `rst` = 1, the outputs are forced to their reset values and no other rule is evaluated. This holds regardless of `start_stop` and regardless of whether a tick would have coincided with that edge.

Phase 3, the testbench is grown one scenario per agent turn.

`timescale 1ns/1ps
module tb;
  `include "check.vh"

  localparam CPT = 4;  // CYCLES_PER_TENTH for fast testing

  reg clk = 0, rst = 0, start_stop = 0;
  wire running;
  wire [3:0] tenths;
  wire [5:0] seconds;

  stopwatch #(.CYCLES_PER_TENTH(CPT)) dut(
    .clk(clk), .rst(rst), .start_stop(start_stop),
    .running(running), .tenths(tenths), .seconds(seconds)
  );

  always #5 clk = ~clk;

  integer i;

  initial begin
    // R9: Power-on state before any rising edge of clk
    check("poweron_running", running, 1'b0);
    check("poweron_tenths", tenths, 4'd0);
    check("poweron_seconds", seconds, 6'd0);

    @(negedge clk); // t=10

    // R10/R11: Reset asserted with start_stop also high (tests reset priority)
    rst = 1; start_stop = 1;
    @(negedge clk); // t=20, after reset edge at t=15
    check("reset_running", running, 1'b0);
    check("reset_tenths", tenths, 4'd0);
    check("reset_seconds", seconds, 6'd0);

    // Deassert reset and start_stop
    rst = 0; start_stop = 0;
    @(negedge clk); // t=30, stable before t=35 edge

    // R12/R13: Pulse start_stop for one edge; running toggles 0 to 1
    start_stop = 1;
    @(negedge clk); // t=40, after toggle edge at t=35
    check("toggle_running", running, 1'b1);
    check("toggle_tenths_hold", tenths, 4'd0);
    check("toggle_seconds_hold", seconds, 6'd0);
    start_stop = 0;

    // R22: Non-reset, non-tick edge; all outputs hold
    @(negedge clk); // t=50, after edge t=45 (counter=1, no tick yet)
    check("hold_running", running, 1'b1);
    check("hold_tenths", tenths, 4'd0);
    check("hold_seconds", seconds, 6'd0);

    // R16/R19: First tick at CPT-th rising edge after running became 1
    //   toggle edge t=35 set counter=0; ticks at t=45,55,65,75 (counter reaches 4)
    //   from t=50: 3 more negedges to t=80
    repeat (CPT - 1) @(negedge clk); // t=60, t=70, t=80
    check("tick1_tenths", tenths, 4'd1);
    check("tick1_seconds", seconds, 6'd0);

    // R15: Hold start_stop high for 3 consecutive edges; running toggles at each
    start_stop = 1;
    @(negedge clk); // t=90, after rising t=85: running 1→0
    check("multi_toggle1_running", running, 1'b0);
    @(negedge clk); // t=100, after rising t=95: running 0→1
    check("multi_toggle2_running", running, 1'b1);
    @(negedge clk); // t=110, after rising t=105: running 1→0
    check("multi_toggle3_running", running, 1'b0);
    start_stop = 0;

    // R17: Pause and resume; in-progress tenth is discarded, count restarts
    start_stop = 1;
    @(negedge clk); // t=120, after rising t=115: running 0→1, counter=0
    check("resume_running", running, 1'b1);
    start_stop = 0;

    // Let exactly 2 ticks happen (each takes CPT edges):
    //   tick at rising t=155 (tenths 1→2), tick at rising t=195 (tenths 2→3)
    //   from t=120, reach negedge t=200: 2*CPT negedges
    repeat (2 * CPT) @(negedge clk);
    check("after2ticks_tenths", tenths, 4'd3);
    check("after2ticks_seconds", seconds, 6'd0);

    // Pause: running 1→0, no tick
    start_stop = 1;
    @(negedge clk); // t=210, after rising t=205
    check("pause_running", running, 1'b0);
    check("pause_tenths_hold", tenths, 4'd3);
    start_stop = 0;

    // One edge paused (counter holds)
    @(negedge clk); // t=220

    // Resume: running 0→1, counter resets to 0
    start_stop = 1;
    @(negedge clk); // t=230, after rising t=225
    check("restarting_running", running, 1'b1);
    start_stop = 0;

    // First tick after resume is exactly CPT edges from t=225 → tick at t=265
    // From t=230: CPT negedges to t=270
    repeat (CPT) @(negedge clk);
    check("resume_tick_tenths", tenths, 4'd4);

    // R18: Toggle takes priority over a coinciding tick
    // After tick at t=265, counter=0. Next tick would be at rising t=305.
    // Apply start_stop on that edge: toggle fires, tick is suppressed.
    repeat (CPT - 1) @(negedge clk); // t=280, t=290, t=300
    start_stop = 1;
    @(negedge clk); // t=310, after rising t=305: toggle instead of tick
    check("toggle_priority_running", running, 1'b0);
    check("toggle_priority_tenths", tenths, 4'd4);  // tick suppressed: still 4
    start_stop = 0;
    // R11 (cont.): Reset takes priority over a coinciding tick
    // Start stopwatch, advance counter to CPT-1, then reset on the tick edge.
    start_stop = 1;
    @(negedge clk); // toggle: running 0→1, counter=0
    start_stop = 0;
    repeat (CPT - 1) @(negedge clk); // counter is now CPT-1; next rising edge would tick
    rst = 1;
    @(negedge clk); // rising edge: reset wins, no tick
    check("reset_over_tick_running", running, 1'b0);
    check("reset_over_tick_tenths", tenths, 4'd0);
    check("reset_over_tick_seconds", seconds, 6'd0);
    rst = 0;
    @(negedge clk); // stable before next edge

    // R20/R21: Wrap-around
    // After reset_over_tick: running=0, tenths=0, seconds=0
    // Start the stopwatch (running 0→1, counter=0)
    start_stop = 1;
    @(negedge clk); // toggle edge
    start_stop = 0;

    // 9 ticks: tenths 0→9, seconds stays 0
    repeat (9 * CPT) @(negedge clk);
    check("tenths9_seconds0_t", tenths, 4'd9);
    check("tenths9_seconds0_s", seconds, 6'd0);

    // 1 more tick: tenths 9→0, seconds 0→1  (R20)
    repeat (CPT) @(negedge clk);
    check("wrap_tenths_to0", tenths, 4'd0);
    check("wrap_seconds_to1", seconds, 6'd1);

    // 589 more ticks: from (t=0,s=1) to (t=9,s=59)
    //   total elapsed tenths from start = 10+589 = 599; 599%10=9, 599/10=59
    repeat (589 * CPT) @(negedge clk);
    check("tenths9_seconds59_t", tenths, 4'd9);
    check("tenths9_seconds59_s", seconds, 6'd59);

    // 1 more tick: tenths 9→0, seconds 59→0  (R21)
    repeat (CPT) @(negedge clk);
    check("fullwrap_tenths", tenths, 4'd0);
    check("fullwrap_seconds", seconds, 6'd0);
    summary;
  end

    #100000;
    $display("CHECK testbench_completed FAIL got=0 want=1 t=%0d", $time);

Phase 4, the final implementation from the specification and an empty module header.

module stopwatch #(
  parameter CYCLES_PER_TENTH = 10
)(
  input clk,
  input rst,
  input start_stop,
  output reg running,
  output reg [3:0] tenths,
  output reg [5:0] seconds
);
  localparam CYC_W = $clog2(CYCLES_PER_TENTH) + 1;
  reg [CYC_W-1:0] cyc;

  // Power-on values before the first rising edge
  initial begin
    running = 1'b0;
    tenths  = 4'b0000;
    seconds = 6'b000000;
    cyc     = {CYC_W{1'b0}};
  end

  // A tick occurs on the edge where the cycle counter would reach CYCLES_PER_TENTH.
  wire at_tick = running && (cyc + 1 == CYCLES_PER_TENTH);

  always @(posedge clk) begin
    if (rst) begin
      // Case 1: Reset (highest priority)
      running <= 1'b0;
      tenths  <= 4'd0;
      seconds <= 6'd0;
      cyc     <= {CYC_W{1'b0}};
    end else if (start_stop) begin
      // Case 2: Toggle (level-sensitive, no tick on this edge)
      running <= ~running;
      cyc     <= {CYC_W{1'b0}};
    end else if (at_tick) begin
      // Case 3: Tick
      cyc <= {CYC_W{1'b0}};
      if (tenths == 4'd9) begin
        tenths  <= 4'd0;
        seconds <= (seconds == 6'd59) ? 6'd0 : seconds + 6'd1;
      end else begin
        tenths  <= tenths + 4'd1;
        seconds <= seconds;
      end
    end else begin
      // Case 4: Hold
      if (running) begin
        cyc <= cyc + 1'b1;
      end
    end
  end
endmodule
